# 电视端付费家长确认闸门（PayGate）设计说明

## 1. 先看清威胁模型：四位 PIN 为什么必然失败

孩子"看会密码"不是偶发事故，而是这类方案的结构性缺陷：

| 缺陷 | 说明 |
|---|---|
| 熵太低 | 四位数字只有 1 万种组合，而电视端往往没有失败锁定或锁定很弱 |
| 肩窥不可防 | 输入过程全家人都看得见，且孩子有大量旁观机会（家长不设防） |
| 静态秘密长期复用 | 一次看会，永久有效；改密码后又会被再次看会 |
| 无法区分操作者 | 密码只证明"知道密码的人"，不证明"是家长本人" |
| 遥控器输入路径单一 | 上下左右选数字的轨迹本身就暴露了 PIN |

结论：**任何"在电视屏幕上输入、且可被旁观的静态秘密"都不能作为独立确认手段。** 新方案必须把秘密移出电视屏幕，并引入"持有物（家长手机）+ 固有特征（指纹/面容/声纹）"。

### 要防的具体攻击场景

1. 孩子趁家长不在，独自拿遥控器连续下单（本案例，主要场景）
2. 孩子旁观家长操作并模仿（肩窥）
3. 孩子拿到家长手机但解不开锁（生物识别兜底）
4. 孩子在电视端暴力枚举 OTP（失败退避 + 服务端计数）
5. 重放抓包到的确认结果（一次性、绑定设备和订单的 approvalToken）
6. 孩子切换到家长档案购买（档案切换本身需要手机端确认，见 §7）

## 2. 总体架构：风险分级 + 因素分层，而不是一道统一的门

```
下单请求
  │
  ▼
RiskEngine 风险判定（纯 Kotlin，可单测，规则可解释）
  │
  ├─ BLOCK ──────────────► 儿童/青少年档案、超额、超次数 → 直接拒绝，提示去家长手机端处理
  │
  ├─ ALLOW ──────────────► 5 分钟信任窗口内的小额（游戏充值除外）→ 免确认直接下单
  │
  ├─ VERIFY_STANDARD ────► 普通消费：四选一
  │     ① 手机推送 + 指纹/面容（推荐）
  │     ② 电视二维码 → 手机小程序确认（无需装 App）
  │     ③ 短信 OTP，遥控器数字键输入（兜底）
  │     ④ TTS 语音问答（无手机场景兜底）
  │
  └─ VERIFY_HIGH_RISK ───► 大额(≥300元)/高频：只接受①②，短信和语音被排除
        │
        ▼
  服务端校验通过 → 一次性 approvalToken（绑订单+设备，60s 有效）→ 凭 token 下单
```

### 为什么这样分层

- **不是每次购买都强验证**——强验证每次都做，老人嫌烦、家长嫌烦，最终会走向"告诉孩子密码"的老路。小额信任窗口把 90% 的日常续费变成无感操作。
- **高风险操作强制强因素**——孩子一次花几千的特征是"单笔大额"或"连续多笔"，这两类被单独拎出来，只接受手机本机生物识别，孩子拿着遥控器无论如何过不去。
- **BLOCK 比 VERIFY 更靠前**——儿童档案从入口就不允许发起付费，不依赖任何密码。

## 3. 四个确认因素的设计取舍

| 因素 | 秘密在哪 | 防肩窥 | 老人可用性 | 适用风险等级 | 主要弱点与对策 |
|---|---|---|---|---|---|
| ① 手机推送+生物识别 | 手机端 | 完全不经过电视 | 高：按一下指纹 | 标准/高风险 | 手机不在身边时不可用 → ②③④兜底 |
| ② 扫码+小程序确认 | 手机端 | 电视只显示二维码 | 高：微信扫一扫是老人已会的动作 | 标准/高风险 | 需有第二个设备；二维码 120s 过期防拍照重放 |
| ③ 短信 OTP | 手机收码、电视输入 | 圆点回显+随机 6 位，旁观只能看到按键位置 | 中：要会看短信 | 仅标准 | 存在被旁观输入的可能 → 数字键直输缩短输入时间；高风险场景禁用 |
| ④ 语音问答 | TTS 朗读、不落屏 | 问题和答案都不显示 | 中：会说话即可 | 仅标准 | 录音重放 → 服务端声纹+语义双校验、问题随机抽、单次有效 |
| 旧四位 PIN | — | 不防 | — | **禁止单独使用**，迁移期仅作为①-④的附加第二因素 | — |

关键交互细节（对应 `ParentGateFragment`）：

- **OTP 不用虚拟键盘**：遥控器数字键 0-9 直接录入，退格键删除，屏幕只显示 `● ● ● ○ ○ ○`。孩子即使旁观，看到的只是按了哪些键位，而 6 位随机码每次不同、2 分钟过期，单次旁观无法复用。
- **语音问题只朗读不显示**：避免家里任何人低头看到屏幕上的问题文本；问题库由服务端从家长注册时录入的私密事实中随机抽取（如班主任姓氏、第一只宠物名字），不使用孩子可查到的公开信息。
- **推送确认页显示脱敏手机号**（`138****6688`）：让老人确认"是发给我的手机"，不会被其他家庭成员的设备误导。
- **默认焦点在①**：上下键切换因素，路径最短的是最安全的选项；老人不需要理解因素差异，跟着默认走即可。

## 4. 防摩擦设计：让正常购买不麻烦

1. **5 分钟信任窗口**：一次确认通过后，窗口内 ≤100 元的会员续费、影片点播不再确认（`TrustSession`）。窗口短、金额小，即使孩子这时接过遥控器，损失也有上界。
2. **游戏充值不享受信任窗口**：本案例的重灾区，每一笔都要确认。
3. **额度硬顶代替逐笔审问**：1 小时 500 / 单日 2000 / 单月 8000 元、单月 30 笔。家长设一次，系统自动兜底，不需要在每笔消费上做判断。额度调整只能在家长手机端做，电视端无入口。
4. **推送是一键操作**：手机通知点开 → 指纹，两步完成，不需要在电视上输入任何东西。
5. **文案说人话**：被拦截时显示"今日累计消费将超过家长设定的 2000 元上限"，而不是错误码。

## 5. 安全机制清单

### 5.1 失败退避（`AttemptThrottle`，服务端有权威计数）

连续失败的锁定阶梯：15s → 60s → 5min → 30min → 24h；连续 10 次失败转人工风控（客服外呼家长核实）。计数在服务端按账号累计，清 App 数据、换设备都绕不过；电视端这份只用于即时 UI 反馈。

### 5.2 一次性令牌防重放

确认通过后服务端颁发 `approvalToken`，与 `paymentId`、设备 ID 绑定，60 秒内有效、只能使用一次。下单接口必须携带有效 token，否则拒绝。即使抓包也无法重放或挪用到其他订单。

### 5.3 Challenge 生命周期

每次确认生成独立 `challengeId`，TTL 120 秒；用户按返回键即调 `cancel` 作废；过期、拒绝、锁定都是显式状态，UI 按状态渲染，不存在"卡住的确认页"。

### 5.4 本地存储

信任窗口用 `EncryptedSharedPreferences`（AES256-GCM）存储。消费统计和额度**只信服务端**，TV 本地不保存可被篡改的累计值。

### 5.5 不做的事

- 不做电视端人脸识别作为主因素：客厅光线复杂、电视摄像头角度固定，照片/视频攻击面大；若设备支持，仅可作为风险评分的辅助信号。
- 不做电视端图形密码/手势：D-pad 轨迹比数字 PIN 更容易被旁观记录。
- 不做"记住密码"：没有任何静态秘密长期驻留在电视端。

## 6. 老人可用性专项

| 障碍 | 对策 |
|---|---|
| 看不清字 | 所有文案 ≥24sp，按钮高 ≥56dp，焦点态加粗描边，3 米视距可读 |
| 不会选 | 默认焦点就是推荐路径，一路按确认即可；推送只需按指纹 |
| 没有/不会装 App | 方案②走微信小程序扫码，不要求安装任何应用 |
| 手机不在身边 | 方案④语音问答，会说话就能用；问题在注册时由子女帮忙录入 |
| 听不清 TTS | 语音问题可重复收听（按确认键重播），8 秒录音上限，支持重试 |
| 多个老人 | 支持绑定多位监护人手机，任一通过即可；每位都有独立脱敏标识 |
| 被锁了不知道怎么办 | 锁定页直接提示"改用家长手机确认"，手机通道不受电视端锁定影响 |

## 7. 配套的账号与档案规则（TV 端代码之外，但必须一起做）

1. **儿童/青少年档案发起的支付直接 BLOCK**（已在 `RiskEngine` 实现）。档案切换到成人需要手机端确认，否则这个闸门可以被"切档案"绕过。
2. **首次绑定监护人在手机端完成**：TV 端只展示绑定二维码，不接受任何在电视上录入的家长凭证。
3. **每笔支付结果实时推送家长微信/短信**：即便确认流程被绕过（如账号被盗），家长也能在分钟级发现并一键退款。
4. **未绑定监护人的账号不允许付费**，引导手机扫码绑定后再买，而不是降级成 PIN。
5. **未成年人模式**与系统级青少年模式联动：国家广电总局《未成年人网络保护条例》及广电总局关于智能电视收费的专项治理要求，未成年人模式下默认关闭付费、续费前二次确认、提供一键退订和退款入口。本方案的 BLOCK 策略与该要求一致，上线前需对照最新监管文件复核文案与退款路径。

## 8. 代码地图

```
tv-parent-gate/
├── build.gradle.kts
└── src/
    ├── main/java/com/example/tv/paygate/
    │   ├── RiskPolicy.kt               # 支付上下文、风险引擎、因素与阈值（纯 Kotlin，无 Android 依赖）
    │   ├── TrustSession.kt             # 信任窗口、加密存储、失败退避
    │   ├── PayGateApi.kt               # 服务端契约：challenge 生命周期、OTP/语音提交、状态轮询
    │   ├── ParentVerificationManager.kt# 流程编排：判定→建挑战→交互→轮询→颁发 token/信任窗口
    │   ├── ParentGateFragment.kt       # 纯 D-pad 遥控器 UI：因素列表、二维码、OTP 直输、语音 TTS
    │   ├── VoiceRecorder.kt            # 16k 单声道 PCM 录音骨架
    │   ├── UiCoroutineUtils.kt         # 生命周期感知的协程封装
    │   └── tv/
    │       └── CheckoutActivity.kt     # 接入方骨架：下单→判定→确认页→带 token 下单的完整链路
    └── test/java/com/example/tv/paygate/
        └── RiskEngineTest.kt           # 风险分级与退避逻辑的单测（11 个用例覆盖关键分支）
```

接入方需要实现/替换的部分：

- `PayGateApi` 的 Retrofit 实例与你们账号体系的鉴权拦截器；
- `ParentGateFragment.Listener` 接到 `onApproved(token)` 后，带 token 调你们现有的下单接口；
- 服务端的 challenge 服务、短信通道、语音校验（声纹+语义）、额度统计与 approvalToken 颁发；
- `VoiceRecorder` 在你们电视芯片上的录音权限与回声消除适配。

## 9. 上线前建议的验证清单

- [ ] 儿童档案下三个支付入口（会员/点播/游戏）全部 BLOCK，且无绕过路径（含切档案）
- [ ] 高风险场景下短信/语音因素在 UI 上不可选（`startChallenge` 的 `require` 也会二次拦截）
- [ ] OTP 输错 3 次出现 60s 锁定，10 次后锁 24h；清应用数据后锁定仍生效（服务端计数）
- [ ] approvalToken 重放、跨订单使用、过期使用均被服务端拒绝
- [ ] 信任窗口在 5 分钟后失效；窗口内游戏充值仍要求确认
- [ ] 遥控器盲测：只给上下左右+确认+返回+数字键，老人能独立完成一次推送确认
- [ ] 二维码 120s 过期后页面自动提示重新发起
- [ ] 中文 TTS 在目标电视设备上可正常朗读，且问题文本不出现在任何日志和屏幕上
